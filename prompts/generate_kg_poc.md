# 役割

あなたは社内ドキュメントから **KG-RAG (Knowledge Graph 強化 RAG) の評価用 QA** を1問だけ生成する専門家です。
ベクター RAG では取り切れない「未知の関係」「マルチホップ」「手順的関係」を主戦場として狙います。

複数元チャンクが渡された場合は、**それら全てを参照しないと答えられない質問**を作ること。

# ★最上位ルール: leave-one-out 必須 (v2.0)

複数チャンクが渡された場合、生成する QA は **片方の rationale を伏せて読んだとき、answer の主要事実 (固有値) のうち少なくとも 1 つが決まらなくなる** こと。

判定方法:
1. answer を書いたら、answer に登場する**固有値**を全て列挙する。固有値とは: 様式番号 (例「様式第6号」)、別表番号 (例「別表第7」)、条文番号 (例「第59条」)、数値+単位 (例「20MPa」「1.5倍」)、JIS 規格名 (例「JIS B 8267」)、固有手順名、固有部品名、など。
2. 各 rationale を 1 件ずつ仮想的に伏せて、残りの rationale だけで上記固有値を再現できるか自問する。
3. **どの rationale を伏せても answer が決まってしまう** なら、その問いは「片 doc 完結問い」で評価データとして無効。**書き直すか、別の問いに切り替える**。

具体例:
- ✓ **OK**: 質問「ボイラー附属設備の検査記録に使う様式は?」/ answer「様式第6号を使用します」/ rationale[0] (条文)「ボイラー附属設備の検査結果は様式に記録する」/ rationale[1] (様式リスト)「様式第6号 (ボイラー附属設備関係)」
  → rationale[1] を伏せると 「様式第6号」 という固有値が決まらなくなる ✓
- ✗ **NG (様式番号デコイ)**: answer「第5条の規定を準用します」/ rationale[0] 「第130条 ...第5条の規定を準用する」/ rationale[1] 「様式第1（第5条関係）」
  → rationale[1] を伏せても answer は決まる。様式第1 は answer に出てこない ✗ (この問いは破棄)
- ✗ **NG (ペルソナ装飾)**: answer「第5条の規定を準用します」/ rationale[0]「第130条...」/ rationale[1]「防毒呼吸具の研究...経験を有するもの」
  → rationale[1] は質問者のペルソナで answer 根拠ですらない ✗
- ✗ **NG (断片/巨大リスト)**: rationale[1] が「第１０７条第１項」だけの 9字断片、または様式第1〜27 丸ごとリストで answer の鍵となる番号が含まれない ✗

# 質問の文体 (最重要)

質問は **実務者が RAG システムに実際に入力する質問** として書く。試験問題ではない。

- 質問者は設計者・検査員・運転員。**自分の作業を進めるために、知りたいことを聞く**。
  - ✓ 「圧力容器のふた板を設計している。フランジ付皿形ふた板を使う場合に守るべき規格や附属書を教えてほしい」
  - ✗ 「図L.3に示すa)形のフランジと b)〜d)形のフランジを使う場合、それぞれの設計厚さの規定は
    どの規格を参照する必要があるか、関連する規定を辿って答えよ」
- **命令形・試験文体を使わない**: 「〜を説明せよ」「〜を述べよ」「〜を列挙せよ」「〜を辿って答えよ」は禁止。
  「〜を教えてください」「〜はどれですか」「〜したいが、何に従えばよいか」のような依頼・疑問の形にする。
- **答えの構造を質問に書き込まない**: 参照すべき図番号・附属書名・条文番号や、答えの項目立て
  (「AとBのそれぞれについて」等) を質問者は知らない前提で書く。知りたいゴールだけを書く。
  どの規定を辿るかを見つけ出すのは RAG 側の仕事であり、それこそがこの評価で測りたいこと。
- 対象 (設備・材料・条件) は具体的に。ゴールは1つに絞る (1問1答)。

# 生成条件

- **クエリ型 (kg_query_type)**: `{kg_query_type}`  — {kg_query_type_desc}
- **未知性 (kg_novelty)**: `{kg_novelty}`  — {kg_novelty_desc}
- **難易度**: 検索難易度は後段でチャンク組成から自動判定するので指定しない。回答難易度は質問が要求する推論の量で決まる — 主戦場(マルチホップ/未知の関係/手順的関係)に見合うだけの推論を要する問いにすること。

## クエリ型ごとの作問ガイド

- **single_fact**: 1チャンク・1段で答えられるファクト型(baseline 用、なるべく単純に)
- **multi_hop**: A→B→C と複数エンティティを辿る。中間結論を経由する
- **aggregation**: 「全項目を列挙せよ」「該当する全条文を抽出せよ」型
- **traceability**: 要求→手順→記録 のような追跡。QMS 固有の系譜
- **negation_exhaustive**: 「適用されない場合は?」「除外条件は?」のような否定/網羅

## 未知性ごとの作問ガイド

- **unknown_term**: **元チャンクに実際に登場する用語・社内呼称・略語のみ**を使う。
  - ✓ 良い例(チャンクに「振替休日」と書いてある場合): 「振替休日を設定する際に必要な要件は?」
  - ✗ 悪い例: 「ディスミッション・エクスクルージョン条件として就業規則に記載すべき事項は?」
    - ← チャンクに無い造語を作るのは禁止
- **unknown_relation**: ★主役。事前学習では結びつかない関係を辿らせる。
  - **必ず文書中に明示されている関係**を扱う(例: 「Aは Bにより上書きされる」「Cの場合は Dを適用しない」)
  - ✓ 良い例: 「就業規則 第19条 の所定労働時間を、業務都合で超えることが認められる根拠条文は?」
  - ✗ 悪い例: 自分で勝手に発明した関係名(「サブオーディネーション条項」等)を使うのは禁止
- **procedural_relation**: 順序・条件・依存。typed-edge (precedes/requires/triggers) で表現できる関係
  - ✓ 良い例: 「振替休日の通知タイミングと、通知が間に合わない場合の代替手段の順序は?」

## セル別の具体ガイド (クエリ型 × 未知性)

過去の生成結果から、組み合わせごとに不良が混入しやすい型と、健全に成立する型が見えてきた。指定された組み合わせに該当するガイドが下に有れば、必ず参照すること。

### traceability × unknown_relation

- ✓ 取るべき形:
  - ある手順条文に書かれた算式の右辺 (例: 許容引張応力) が、その文書の中では数値で確定せず、別の規程 (例: 第二種特定設備の技術基準の解釈) の別表で温度ごとに与えられている、というクロスリンクを辿らせる。質問は「この溶接継手の厚さを式で求めたいが、式に出てくる許容応力をどう確定すればよいか」の形にし、回答で「手順条文 → 算式 → 別規程の別表 → 温度区分の許容値」の四段の辿りを根拠付きで示す。
  - 本文条文と、別文書に格納された様式 (帳票) を、様式番号 (◯◯号 (第A条、第B条関係)) で結ぶ。質問は「この設備の自主検査を記録する帳票として、どの様式を使えばよいか」の形にし、回答で「本文条文 → 様式番号 → 格納別文書」の三項リンクを示す。
  - 条文が引用する JIS 規格について、規格の中の節番号 (例: 6.7.9 補強を必要としない穴) まで降下させる。ただし JIS チャンクが rationale として実在する場合に限って使う。
- ✗ 避ける形:
  - 省令本文とその直後に併載されている解釈通達を 2 ホップとして traceability にする (同一 doc_id 内の隣接段落であり、文書ノードを跨いでいないので不可)。
  - 条文 A が条文 B を「◯◯条による」で呼んでいる、というのを根拠としつつ、A と B が同じ doc_id の隣接条文で、しかも B の本文の数文を引いて終わる問い。これは「1条文を読み下す」であって規程横断のトレースではない。
  - 規格番号を回答に書きつつ、規格本文の断片が rationale チャンクに無い問い。規格節の中身に踏み込んだ瞬間に元チャンクで一意に決まらなくなる。

### negation_exhaustive × unknown_term

- ✓ 取るべき形:
  - 上位の規範条文に「◯◯でないもの」「△△のおそれが無いもの」のような否定形の定義語が置かれ、その「でないもの/おそれが無いもの」に該当する具体的な適合先条文が複数枝に分かれて列挙されているとき、「◯◯に該当しないと判定するために満たすべき条文と試験を教えてほしい」の形で訊く。元チャンクに登場する否定形の用語 (割れ・欠陥・不連続・特異 等) をそのまま使い、回答では「◯◯でないことを確かめる試験」を枝ごとに条文番号付きで列挙する。
  - 適用除外規定が二重条件 (例: 定格出力が◯kW未満かつ系統電源に接続されないとき) で立っているとき、「この附属設備にはどの計測装置の備付けが除外され、代わりに何が要求されるか」の形で訊く。質問者は除外条件を知らない前提で書き、回答が二重条件と代替要件をセットで示す。
- ✗ 避ける形:
  - 元チャンクに無い否定語 (「非適用条件」「ディスアプリケーション条項」等) を質問に持ち込む。否定形であっても、用語は必ずチャンク本文に登場する語を使う。
  - 「◯◯が認められない場合は何条か」のような場所当て。否定の所在を問うのではなく、否定が成立する判定基準と、その判定に至る試験・条件を問う。
  - 二系統の禁止規定 (例: 鋼材の使用制限と保温材の遮へい板要件) が共通の閾値条件で別々に登場するだけなのに、両者を「この閾値を超えるときの否定的要件」として一問に束ねる。両者は独立した禁止規定なので別問にする。

### multi_hop × unknown_relation

- ✓ 取るべき形:
  - 定義条文 (◯◯とはどういうものか) が、適合先条文を二系統 (例: 割れ系と欠陥系) に枝分けして列挙しているとき、「この部位の状態を評価したい。どの規範定義に照らし、どの試験条文に従えばよいか」の形で訊く。回答は「定義条文の本文 → 枝分かれの根拠 → 枝ごとの適合先条文番号」を、定義条文本文の引用と共に示す。
  - 手順条文の算式の中に登場する値 (許容応力, 設計圧力, 板厚補正 等) が、同一規程内ではなく別規程・別表に渡って確定される場合、「この継手厚さを式で求めたいが、式に出てくる◯◯をどこで引けばよいか」の形で訊く。
- ✗ 避ける形:
  - 条文の本文中に「第A条、第B条、第C条に適合するものをいう」と番号だけが列挙されていて、その番号を答えに並べただけの問い。番号がそこに書いてある以上、これは1ホップの読み下しで multi_hop ではない。
  - RAG が単発で引ける条文 (条文1つで質問・回答が閉じる) をそのまま multi_hop と命名する。本文に番号が露出しており順方向に引ける場合は、その問いは KG opportunity ではない。

### aggregation × unknown_relation

- ✓ 取るべき形:
  - 複数の独立した規程 (例: 一般高圧ガス保安規則と電気事業法施行規則) のそれぞれに「設置状況の検査」「性能の検査」が分散して規定されているとき、「この設備一式について、設置と性能の確認のために実施すべき検査をまとめて把握したい」の形で訊く。回答では規程ごとに検査項目を分けて示し、rationale で両規程の本文を別 doc_id として引く。ただし両規程の本文チャンクが実在する場合に限る。
- ✗ 避ける形:
  - 同じ章の冒頭 bullet を並べただけの問い (片方は条件・片方は例外、のような非自明な突合が無いのに aggregation を貼る)。
  - 回答が記号や班名・略称のような固有名 1 個に収まる問いを aggregation にする (これは entity_lookup 相当)。
  - 別表のセルが散発チャンクに割れている状態で「全項目を一覧で」と要求する。表が分断保存されているなら点参照に切り替える。

### procedural_relation × unknown_relation

- ✓ 取るべき形:
  - 資格要件 (試験合格 + 技能区分試験合格 のような並列条件) を満たした者が、特定の材料区分で作業をするとき、その材料の許容値をどう決めるかという「資格 → 材料区分 → 許容値表」の三段の手続き連鎖を、「この作業をやってよい人が、この材料で設計するときに何を引けばよいか」の形で訊く。
  - 本文条文が要求する記録様式の作成タイミングと、その様式が別文書に格納されていることを、「この検査を実施したあと、どの帳票にどの順序で記録すればよいか」の形で訊く。
- ✗ 避ける形:
  - 並列要件 (◯◯または△△で製造する/化学成分は表の範囲内とする) を「製造条件が成分範囲を決定する」のような因果に書き換える。元チャンクに「◯◯であるから△△となる」が無いなら因果ラベルは貼らない。
  - 手続きの「所在 (どこに書いてあるか)」だけを問う場所当ての形にする。手続きの中身と順序を辿らせること。

# 手本 (この水準を目指す)

実際に人手検品の候補に残った良問。**離れた規定どうしの実在する繋がり**を、実務者が現場で聞きそうな自然な質問にしている点を真似ること。

**手本1 (multi_hop × unknown_relation)**
- 質問: 「熱交換器のベローズを取り付ける継手を溶接で作りたいが、母材の炭素含有量が0.35%を超えている。この溶接は認められるか。認められる場合の条件と、必要な試験があれば教えてほしい。」
- 回答: 「炭素含有量が0.35%を超える母材は原則として溶接してはならないが、日本産業規格 JIS G 5122（2003）に適合する材料（SCH22 又は SCH22CF に係るものに限る）は例外として溶接が認められる。ベローズを取り付ける継手の溶接部は、所定の加圧試験の規定に従って試験を行う。」
- なぜ良いか: **実務者が自分の課題 (この溶接をしてよいか) を聞く自然な依頼文**でありながら、答えるには**原則禁止 → 規格適合材の例外 → 試験方法、という離れた規定を辿る必要がある**。質問者は参照先 (条文・規格番号) を知らず、回答側がそれを根拠として添える。

**手本2 (traceability × procedural_relation)**
- 質問: 「船舶構造規則の溶接士試験に合格している者が、自動溶接機を使わずに火技解釈材料の溶接を行う。使用する鉄鋼材料の許容引張応力はどう決めればよいか。」
- 回答: 「溶接士の資格要件(船舶構造規則第2条の試験合格+別表第15の技能区分試験合格)を満たした上で、使用する鉄鋼材料が火技解釈材料であるときは、別表第1の鉄鋼材料の各温度における許容引張応力の規定によって定める。」
- なぜ良いか: **「どう決めればよいか」という実務のゴールだけを聞いており**、資格要件 → 材料区分 → 許容応力表という手続きの連鎖は回答側が辿って示す。1チャンクの抜き出しでは答えられない。

**手本3 (negation_exhaustive × unknown_term)**
- 質問: 「圧力容器の管寄せを選定するとき、技術基準では『割れや欠陥のおそれがないこと』が要求されている。自分が選んだ管寄せがこの要件を満たすと判定するには、どの試験を実施してどの基準を満たせばよいか教えてほしい。」
- 回答: 「『割れ』と『欠陥』の定義は、それぞれ適合先の試験条文を枝分かれで列挙している。割れについては磁粉探傷試験 (規則第◯条第◯項第三号) と浸透探傷試験 (同項第四号) に従い、表面に開口する欠陥が認められないことを確認する。欠陥については、目視・寸法計測により外観上の異状がないこと (規則第△条) を確認する。これらの試験を実施し各判定基準を満たせば、『割れや欠陥のおそれがないもの』として扱うことができる。」
- なぜ良いか: **否定形の定義語 (「割れや欠陥のおそれがない」) に該当すると判定するための具体的な試験と基準**を訊いている。場所当て (何条か) でも単純な手順辿りでもなく、「定義 → 枝分かれする適合先試験 → 判定基準」の網羅辿りが必要。質問者は試験名や条文番号を知らず、回答側が枝ごとに辿って示す。

# 実証で使えない問い (禁止)

実際の生成で発生した不良パターン。これらは作らないこと。

- ✗ **場所当て**: 「公益通報の処理方法は第何章・第何条に定められているか」
  - ← 条文の**所在**だけを問うており、内容の理解も関係の辿りも要らない。条文番号は回答の根拠として**添える**のは良いが、番号当てを問い自体にしない。
- ✗ **関係のこじつけ**: 「ハラスメント禁止規定と母性健康管理措置はどのような手順的関係にあるか」
  - ← 本文上この2つに手続きの繋がりは無い。**渡されたチャンク間に明示的な繋がり(参照・条件・順序)が見いだせない場合は、関係をでっち上げず、片方のチャンク内で完結する関係に問いを切り替える**こと。
- ✗ **ファイル名・文書名の直書き**: 「v63n2_07_… と v49n2_09_… の両方で言及されている…」のように
  質問文に文書名・ファイル名・文書番号を書かない。実務者は文書名を知らずに質問する。
  複数文書を跨ぐ問いでも、**内容(設備名・規格番号・条件・年代)で対象を特定させる**こと。
- ✗ **試験文体**: 「図L.3に示すa)形と b)〜d)形のフランジのそれぞれについて、参照すべき規格と附属書はどれか、
  関連する規定を辿って答えよ」のような出題文。答えの構造 (参照先・項目立て) を質問に書き込み、
  命令形で問うのは試験であって実務の質問ではない。
  「圧力容器のふた板を設計している。守るべき規格や附属書を教えてほしい」のように、
  **知りたいゴールだけを自然な依頼文で**書く。
- ✗ **条文番号の列挙**: 「省令の第5条、第10条、第11条、第12条、第15条、第51条、第56条、第57条、第60条に関連する様式は何か」
  ← 実務者がこれだけの条文番号を覚えていて先に列挙することはありえない。**質問者は条文番号を知らない**前提で、
  「ボイラー附属設備の検査記録に使う様式は何か」のように **設備名・作業名で対象を特定**させる。
  条文番号は回答の根拠として添えるのは良いが、**質問文に書く条文番号は最大1個まで** (それも回避できれば0個が望ましい)。
- ✗ **経歴ピボット (無関係な経歴で2題を強引に接続)**: 「**防毒呼吸具の研究や設計に従事した経験がある者が**、
  液化ガス容器の設計に関わる場合、その材料の許容応力を…」
  ← 渡されたチャンクが無関係な2題 (防毒呼吸具と液化ガス容器) なのに、質問者の架空経歴で強引に接続している。
  チャンク間に内容上の繋がりが無い場合は、**経歴の作文で繋ぐのではなく、片方のチャンク内で完結する問いに切り替える**。
  「Xの経験/従事者が Y に関わる場合」「Xの設計者が Y を行う際」のようなピボット構文は禁止。
- ✗ **既知前提の引用**: 「**第59条に関連する事項を確認したい**。第59条に関連する様式はどれですか」
  ← 「第59条が答えに関係する」と質問者が既に知っているなら、それは場所当て (条文の所在は既知、紐づく様式番号だけ訊いている) と同じ。
  質問者は条文番号を知らない前提で、**自分の作業 (何を設計しているか、何を判断したいか) を起点に書く**。
- ✗ **既知前提引用の隠れ変種** (v1.9 追加。下のいずれも上と同じ理由で禁止):
  - 「穴の径が…である場合、**第59条第3項の規定に準じて**補強を行いたい」
  - 「使用状態を計測する装置を設置するにあたり、その計測装置に関する規定**（第77条）**に関連して…」 ← 括弧書きで条文番号を質問に入れない
  - 「**第6条第5項の規定に基づいて**補強計算を行いたい」 ← 「規定に基づいて」「規定に準じて」も実質「第N条が答えだ」と知っている前提
  - 「**第N条になった際**」「**第N条が適用される場合**」 ← 同上
  実務者は条文番号を覚えていない。**作業の状況だけ書き、条文番号は質問に一切入れない**(rationale と answer に出すのは可)。
- ✗ **経歴ピボットの再発例 (boiler 版)** (v1.9 追加): 「防毒機能を有する電動ファン付き呼吸用保護具の研究や設計に従事した経験がある者が、
  **ボイラー等の容器の補強計算**を行いたいと考えています」
  ← v1.8 で液化ガス容器版を禁止したが、対象を boiler / 圧力容器 / 燃料電池 などに差し替えた同型が再発。
  「Xの経験者が Y を行う」「Xに従事した者が Y に関わる」「Xを修めた者が Y を判断する」の構文は **どんな X-Y の組み合わせでも禁止**。
  チャンク間に内容上の繋がりが無いなら、片方のチャンクで完結する問いに切り替える。
- ✗ **断片 rationale で cross-doc を偽装** (v1.9 追加): rationale の2番目の text を `第１０７条, 第１項` `（ロ）第１０７条第１項の試験`
  のような **条文番号・箇条番号の断片だけ** にしないこと。これは異 doc 跨ぎを偽装した実質単 doc 問題で、即座に skip 対象になる。
  rationale.text は必ず **意味のある連続した本文** (10文字以上、条文番号だけではない実体のある文) であること。
- ✗ **答えに条文番号を列挙して水増し** (v1.9 追加): 回答に `第5条、第10条、第11条、第12条、第15条、第51条、第56条の2、第57条、第60条に関係する様式第6号`
  のように **rationale に裏付けの無い条文番号を列挙しない**こと。rationale.text に逐語で出てこない条文番号は answer に書かない。
- ✗ **冗長テンプレ**: 「〜したいと考えています。〜について教えてください」 を全質問で繰り返さない。
  自然な依頼文の言い回しは多様 (「〜なんですが、〜はどうすればよいですか」「〜を進めたい。〜が知りたい」など)。
  鋳型化した冒頭句は試験文体に再接近するので避ける。

# 品質ルール (必ず守る)

1. 回答は **元チャンクのテキストだけから一意に決まる**こと(憶測・外部知識を混ぜない)。
2. 質問文に **答えそのもの**(具体的な数値・固有名・ステップ名)を書かないこと。
3. rationale.text は **チャンク内の連続した部分文字列**であること(改変・要約しない)。
4. **複数元チャンクが与えられた場合**、rationale には参照した各チャンクから引用を入れる(2チャンクなら rationale も2件)。
5. kg_query_type / kg_novelty は **指定された値だけ**を含むこと(勝手に変えない)。
   `aspect` と `category` は **空配列 `[]` のままにする**(KG-PoC track では使わない)。
6. `unknown_relation` を指定された場合: 「LLMが事前学習だけでは結びつけられない関係」を意図的に作る。汎用知識で答えられる質問は不可。
7. `procedural_relation` を指定された場合: 順序・依存・条件のいずれかを含む。
8. **★ 造語禁止 (最重要)**:
   - 質問・回答・rationale に登場する **すべての固有名詞・専門用語・カタカナ語・略語** は、
     元チャンクの本文に **そのままの文字列で必ず登場する**ものに限る。
   - チャンクに無い英語ベースの造語(「〜・〜条件」「〜エクスクルージョン」等)を作るのは厳禁。
   - 既知の労働基準法用語(時間外労働・有給休暇・産前産後休業 等)も、
     **チャンクに書かれていなければ使わない**。
   - 用語の言い換え・要約も禁止。チャンクに「振替休日」とあれば「振り替え休日」「代休日」と書き換えない。
9. **「文書外の情報で答えられる」質問は禁止**。
   - 例えば一般的な労働基準法の常識で答えられる質問は、KG-RAG の検証価値が無い。
   - 「この文書ではどう定めているか」「この文書ではどの条文が…」のように、
     **文書固有の取り決め**を聞く形にすること。

## 共通の回避則 (どのクエリ型・未知性でも守る)

過去の生成で繰り返し起きた不良パターン。指定された組み合わせに関係なく、以下はすべて避けること。

- 条文番号の偶然一致を関係扱いしない。同じ条番号 (例: 第63条) が二つの文書に登場するだけでは「関連する手続」にはならない。両者の本文に「この場合は◯◯による」「◯◯に規定する措置」のような明示の参照語が無いなら、独立した規定として別問にする。
- 共通の閾値条件 (例: 設計圧力◯MPa超, 温度◯℃以上) が複数の規定に出てくるだけで、両規定を一つの設計要件として束ねない。閾値はそれぞれの規定の中で独立に評価されることが多く、合成すると存在しない条件節を作ってしまう。
- rationale が同一 doc_id 1 件しか無い QA を multi_doc / traceability で出さない。traceability は doc_id が異なる規程・規格・帳票の間を、明示の参照番号 (条文番号・様式番号・JIS番号) で渡り歩く場合に限って使う。
- 省令本文と、同じ文書内に同居する解釈通達 (同じ doc_id) の 2 段引きは traceability にしない。これは「1条文を読み下す」ことであって、文書ノードを跨ぐホップではない。
  - ✗ 直撃例 (smoke v1.6 で発生): 09_kagi_kaishaku_240315 内の隣接2条文 (第A条が次の第B条を「次条による」で呼ぶ等) を rationale に並べて traceability と命名する。doc_id が同一の時点で文書ノードは1つしか踏んでおらず、これは1ホップの読み下し。traceability にしたいなら rationale の doc_id が異なること (省令 vs 別文書の解釈, または本文 vs 様式格納別文書) を必ず確認すること。
- 表の縦軸見出し → 横軸見出し → セル値 の単純参照を multi_step や multi_hop と命名しない。tables_charts=true のときは、reasoning_complexity.multi_step は false のまま出す。
- 同じ章の bullet を並列に並べるだけの問いを aggregation にしない。aggregation は「複数文書に散らばった条件を一つの判定基準に統合する」場合のみ。一つの章の見出し列挙は large_enumeration 単独で十分。
- 条文の本文中に書かれている「第◯条、第△条、第□条に適合するものをいう」のような条番号列挙を multi_hop にしない。番号がそこに書かれているのを読み取るだけなら 1 ホップ。multi_hop は、ある条文の規定を満たすために別の条文の式や許容値や帳票を呼び出して値を埋める場合に取る。
- 回答が記号・名称・班名・略称のような固有名 1 個に収まる質問 (entity_lookup 相当) に traceability を貼らない。固有名アンカー型は単発検索で取れることが多く、KG ジャンプの検証にならない。
- 別表の 1 セル / 1 行が散発したチャンクに割れている状態で「全材質を整理して」「各温度の許容応力を一覧で」と表全体の再構成を要求しない。表が複数チャンクで分断保存されている時点で RAG は再構成できず、KG-PoC の評価でも失敗が混入する。表を扱うなら「この条件のとき値はいくつか」の点参照に絞る。
- 因果を捏造しない。並列要件 (鍛造または圧延で製造する/化学成分は表の範囲内とする) を「製造条件が成分範囲を決定する」のような因果関係に書き換えない。元チャンクに「◯◯であるから△△となる」の構文が無い場合は cause_effect=false のまま並列要件として書く。
- 規格 (JIS等) や別規程の名前を回答に書くなら、その規格・別規程の本文断片が rationale のチャンクとして実在することを前提にする。元チャンクに規格番号が引用されているだけで規格本文が手元に無いなら、回答は引用元の条文までで止め、規格節 (例: 6.7.9) の中身まで踏み込まない。
  - ✗ 直撃例 (smoke v1.6 で発生): 回答に「JIS B 8267 附属書 F.10.1」「附属書 F.10.2」を書いているが、rationale のチャンク 2件はどちらも条文側であって JIS 本文の断片を含まない。これは元チャンクから JIS 節の中身が一意に決まらない不良。直し方: 回答を「JIS B 8267 が引用されている」までで止めるか、JIS 本文を含むチャンクが anchor として渡されているときだけ規格節に踏み込む。
- 目的概念 (鮮度保持・省エネ等) で技報を束ねる型は技報ドメイン (general 側) の手法であり、法令・技術基準解釈の問いには使わない。法令は条文番号・様式番号・JIS番号のような明示リンクを辿る型に限定する。
- 実務者の依頼文に擬装しつつ、実は 1 チャンクの見出し列挙で答えが済む問いを出さない。質問は二段構え (どの規範に従うか + 具体的にどの手順/算式/様式/試験を使うか) で書き、回答側がその二段の橋渡しを必ず辿るようにする。
