01

全体像 — 7段パイプライン

元文書を入れると QA データセットが出てくる。各段は同名ファイルに上書き出力し、途中から再開できる。中核思想は 「生成 LLM と判定 LLM の自己ループを、決定論チェックと実走検証で外から殴る」。

data/docs/  — 元文書 (.txt / .md / .pdf)
① chunk
STAGE 1chunk — 文書をチャンクに分割
再帰分割 + 見出し追跡 + 参照識別子抽出。トラック非依存。
data/chunks/  — 1 doc = 1 JSONL
② generate
STAGE 2generate --track general | kg_poc
観点抽選 → アンカー選択 → LLM 生成 → 9段の生成後検査。ここでトラック分岐。
data/raw/  — batch_YYYYMMDD_HHMM.jsonl
③ filter
STAGE 3filter — 判定LLM 4観点 + 重複検知 + 逐語根拠照合
answerability / grounding / leakage / difficulty_match をしきい値で絞る。共通。
data/filtered/  — 合格 QA
④ 任意の後付け段
OPTIONALrag-verify / probe / answer-grounding
rag-verify: vector RAG が解けるかを実走。probe: 素の LLM が答えられるか (kg_poc)。answer-grounding: rationale の leave-one-out。いずれも QA に信号を後付けする。
⑤ review
STAGE 4review / review-kg — 人手 accept / edit / reject
Streamlit UI。トラック別チェックリストを全部チェックで Accept 解放。
data/reviewed/  — コミット対象

stats / stats-kg はどの段の JSONL でも可視化でき、RAG検証タブで不一致(=KG候補)を目視できる。

設計の核: 生成 (Gemma系 vLLM) と判定 (Azure gpt-4.1系 / Claude) を別モデルにして自己評価バイアスを断つ。さらに逐語照合・トポロジ算出などLLM を通さない決定論チェックを随所に挟み、LLM が「もっともらしく嘘をつく」経路を機械的に塞ぐ。

02

2つのトラック — 何を測りたいか

同じパイプラインから、目的の違う2種類の評価セットを作れる。分岐点は generate の --track だけ。診断4軸と難易度は両者共通で、違うのは「主タグ」。

general 総合能力測定 (既定)

RAG が「広く」どんな質問形に弱いかを網羅測定する。

  • 分類軸: 25観点 × 5カテゴリの1階層
  • 定義: aspects.py
  • 配分: ループ毎に25観点からランダム抽選
  • 主タグ: category[] / aspect[]
  • 専用コマンド: review / stats

kg_poc KG-RAG 優位の実証

KG-RAG が単純ベクター検索より勝てる場面を計画的に並べる PoC 用。

  • 分類軸: 5クエリ型 × 3未知性 = 15セル + プロービングで known/unknown
  • 定義: tracks/kg_poc.py
  • 配分: --mix qt:nov=N で明示 (未指定は15セル等分)
  • 主タグ: kg_query_type / kg_novelty / llm_knowledge
  • 専用コマンド: review-kg / stats-kg / probe
運用規約: 1ファイル1トラック。 生成時の --out をトラック別に固定 (general→data/raw_general/, kg_poc→data/raw_kg/)。混在ファイルを作らなければ --track 切替に頼らずに済む。トラック判定は「kg_query_type か kg_novelty のどちらかが non-None なら kg_poc、両方 None なら general」という単純ルール (review_app.py:357)。
03

チャンク化と参照識別子抽出

chunker.py。全形式で「参照識別子」を正規表現で拾って references に格納するのが後段の要。この参照が ReferenceFollow 戦略の材料になる。

.txt / .md / .pdf を rglob で列挙
拡張子で分岐

📄 .txt

全体を1ブロックとして再帰分割。page=None。

📝 .md

見出し #〜###### のスタックを辿り、各チャンクに section_path を付与してから分割。

📕 .pdf — pypdf

ページ単位で抽出 → 再帰分割。page を保持。

📗 .pdf — Azure DI

prebuilt-layout の Markdown を経由しページ番号 + 見出しを両取り。結果は .pdf.di.md にキャッシュし、PDFより新しければ再呼出ししない。

再帰分割アルゴリズム _recursive_split

優先度順の区切りパターンで、最大チャンクがサイズ内に収まる最初の粒度を選ぶ。既定 chunk_size=800 / chunk_overlap=100。

段落 \n\n+ → 文末 。．.!? → 改行 \n → 空白 \s+ → 1文字ずつ

分割後は _merge でサイズ上限まで詰め、境界で overlap 文字だけ前チャンク末尾を引き継ぐ。

参照識別子の抽出 extract_references

本文 + section_path から、他の文書 / 章節 / 規格 / 帳票を指す識別子を正規表現で拾い、出現順を保って重複排除する。

種別正規表現 (要約)例
規格番号JIS [A-Z] 4桁 / ISO / IEC / ASMEJIS Z 2241, ISO 9001
章節条項第N章 / 第N節 / 第N条 / 第N項第3章, 第15条, 第2項
図表・附属別表N / 附属書[A-Z]別表2, 附属書A
項番号N.N.N項5.2.3項

discover-patterns — 追加発見 (任意・1回)

組み込み正規表現で拾えない社内文書ID (DS-MEC-104 等) や独自記法を LLM に列挙させ、data/chunks/_discovered_patterns.json に保存 → 以降の chunk で自動適用。3つのガードレールで暴走を防ぐ:

1

コンパイル検査

Python re でコンパイルできない正規表現は捨てる。

2

空マッチ排除

サンプル内で1件もマッチしないパターンは捨てる (幻覚除去)。

3

貪欲パターン排除

サンプルの5%以上を覆う \d+ のような貪欲パターンは捨てる (小サンプルでは検査免除)。

04

アンカーチャンク選択戦略

sampling.py。生成する QA の「問いの型」に合わせて 1〜3 個のチャンクを選ぶ。この段が QA の難易度と検索の性質を決める、パイプラインで最も繊細な部分。

2段フィルタ: 適合述語 → 戦略

AnchorSampler.select(aspect) は、まず観点ごとの適合述語でチャンクプールを絞り、その上で観点別の戦略を回す。

STEP 1適合述語でプールを絞る ASPECT_COMPATIBILITY
例: simple_table は表マーカー (|---/<table>) を含むチャンクだけ。standards_reference は JIS/ISO で始まる参照を持つチャンクだけ。適合0件なら警告して全プールへフォールバック (バッチ要約に compat_misses として出る)。
STEP 2戦略でトポロジを組む ASPECT_STRATEGIES
multi-chunk 観点は「複数チャンクの組成を作れるまで最大20回再抽選」。どうしても作れなければ difficulty_misses を立てて None を返し、生成側が skip。

5つの戦略

戦略ねらい適用観点
SingleChunk1チャンクをランダム。単一観点20種のフォールバック上記以外の20観点
SameDocRemote
(n=2, gap=3)		同一文書内で位置が3以上離れた遠隔ペア。可能なら別トップ見出しを優先remote_reference
ReferenceFollow
(n=2)		参照番号 (第N条→本文/別表) を逐語で辿って繋がる2チャンク。「似てるが無関係」を避けるstandards_reference
reference_follow (kg)
MultiDocByEmbedding
(n=3, floor=0.5)		埋め込みコサイン類似で話題が近いチャンクを集めるmulti_source_integration
MultiDocByEmbedding
(n=2, distinct_doc,
floor=0.55)		異文書強制 + 参照番号の重なり必須 + リスト専用チャンク除外multi_doc_reference

偽の「多文書」を作らせない防御: force_distinct_doc=True のとき異文書パートナーが見つからなければ、同文書で水増しせず [anchor] 単独で返す。こうしないと「2チャンクだが1文書」の偽多文書が生まれ、生成側の early-skip が機能しなくなる (2026-06-17 修正)。require_article_overlap で「偶然の話題類似ペア (例: 防毒呼吸具 × 液化ガス容器)」も切る。

検索難易度の決定論的算出

難易度は乱数で割り当てない。 retrieval_level は LLM を介さず、アンカーのトポロジ (文書数・位置差) だけで決まる。

len(anchors) ≤ 1 → Easy 単一チャンクで完結
doc数 ≥ 2 → Hard 複数文書横断
同一文書内の最大位置差 ≥ 10 → Hard 遠隔参照級
それ以外 → Medium 同一文書・複数チャンク

同時に compute_retrieval_difficulty が診断bool群 (multi_doc, multi_chunk, low_locality≥3, remote_reference≥10, chunk_size_large≥1200字) を埋める。意味依存の軸 (abstraction_discrepancy / vocabulary_mismatch) は質問依存なので False のまま残す。

05

QA 生成ループ

generate.py。--n 回ループし、毎回「スペック決定 → アンカー選択 → early-skip → LLM 生成 → 検証 → 書き出し」を回す。

1イテレーションの流れ

1

スペック決定

general: 25観点から1つランダム抽選。kg_poc: 事前構築した「セルキュー」から (query_type, novelty) を取り出す。

2

アンカー選択 + early-skip

§04 の戦略でチャンクを選ぶ。None なら skip。異文書跨ぎが本質の戦略 (multi_doc_reference / multi_source_integration / multi_hop / reference_follow) で単一 doc に縮退したら早期 skip。

3

プロンプト構築

アンカーチャンク群 + 観点の説明/良い例/悪い例 + Gold Seed から3件の Few-shot を注入。

4

LLM 生成

force_json=True / max_tokens=4096 で JSON mode。壊れた JSON や文字列途中切断を抑制。

5

強制上書き + 決定論確定

kg_poc では LLM がスペックを下げてくる (multi_hop 指示に single_fact を返す) ので kg_query_type/kg_novelty を生成後に再代入。retrieval_level/retrieval_difficulty もアンカーから決定論的に確定。

6

9段の生成後検査 (次節)

1つでも引っかかれば skip。すべて通ったものだけ JSONL に追記。

kg_poc のセルキュー構築 _build_kg_cell_queue

--mix 指定あり

各 (qt, nov, count) を count 個に展開してシャッフル。合計が n より多ければ切り詰め、少なければ mix 内セルから埋め足す。

multi_hop:unknown_relation=10,
traceability:procedural_relation=8

--mix 未指定

全 15 セル (5 query_type × 3 novelty) に等分。divmod(n, 15) で基本数を配り、余りをランダムなセルに割り当ててからシャッフル。

KG スペックは _kg_aspect_for_strategy で既存のアンカー戦略キーに写像して再利用する: single_fact→SingleChunk、multi_hop/traceability→ReferenceFollow (実在参照で繋ぐ)、aggregation→MultiDocByEmbedding。関係を問う組で埋め込み類似ペアを使うと「似てるが関係が無い」問いが判定で大量死するため、実在参照辿りを優先する。

06

9段の生成後検査ゲート

生成 LLM は「もっともらしいが評価に値しない QA」を量産する。判定 LLM に投げる前に、LLM を使わない正規表現/照合ベースの機械検査で不良型を落とす。1つでも引っかかれば skip。

すべて「該当したら skip」する拒否検査
detect_fabricated_terms
質問/回答にある4文字以上の片仮名語が、どのアンカーにも無ければ LLM の造語。破棄。
…single_doc_rationale
アンカーが2 doc以上なのに rationale が1 docに縮退 = 異doc跨ぎが偽装。破棄。
…place_finding_question
「どの条文」「第何条」等の場所当て。内容理解を測れないので破棄。
detect_article_enumeration
質問文に条文番号が3個以上 = 答えのヒントを質問側に書いた試験文体。破棄。
detect_career_pivot
「Xの経験者がYに従事する場合」= 無関係2題を架空経歴で強引接続。破棄。
…known_premise_quote
「第N条に関連する様式は」= 答えの所在を既知前提で引用。場所当ての変種。破棄。
detect_fragment_rationale
rationale が条文番号断片だけ (「第107条第1項」) = cross-doc 偽装。破棄。
detect_short_rationale
rationale.text が30字未満 = 番号断片で配列を水増し。破棄。
…ungrounded_answer_tokens
回答中の固有値 (様式第6号/20MPa/第59条) がどの rationale にも逐語で無い = 捏造/裏取り不足。破棄。
なぜ機械検査か: これらは判定 LLM でも見逃しやすい「不良の型」。正規表現で確実に落とせば、高価な判定 LLM 呼び出しを無駄にせず、判定の通過率も上がる (実測で通過率が数倍改善した既定値がコードにコメントされている)。逐語照合は空白除去 + 全角数字→半角の正規化を挟んで LLM の整形差を吸収する。
07

判定フィルタ — 4観点 + 決定論 + 重複検知

filter.py + prompts/judge.md。生成とは別の判定 LLM (Azure gpt-4.1-mini など) で各観点を採点し、しきい値で絞る。判定 LLM を使う軸と使わない軸を明確に分ける。

raw QA + アンカーチャンク
判定LLMjudge.md の4セクションを個別プロンプトで採点
[ANSWERABILITY] 1-5 / [GROUNDING] 1-5 / [LEAKAGE] pass·fail / [DIFFICULTY_MATCH] で実態レベルを測り answer_level を上書き確定。temperature=0.0。
決定論rationale_grounded + uniqueness
rationale_grounded: rationale.text がアンカーに空白無視で逐語含まれる割合。uniqueness: 埋め込みコサインで他QAとの最大類似度 (1 − sim)。
しきい値
keep / drop1つでも下回れば drop、理由をログ出力

判定軸としきい値

観点種別既定しきい値誰が測るか
answerability1〜5≥ 4.0判定LLM
grounding1〜5≥ 4.0判定LLM
leakagepass / fail--skip-leakage で無効化可判定LLM
difficulty_matchaligned / too_easy / too_hard棄却には使わずタグのみ (--reject-too-easy で too_easy 棄却)判定LLM
uniqueness0〜1cos > 0.92 で重複扱い埋め込み
rationale_grounded0〜1≥ 0.5 (半数逐語必須)決定論照合
チャンク選択の工夫 _find_chunk_texts: 同一 (doc_id, page) には複数チャンクがあり得る (PDFは1ページ最大6チャンク、.txtは page=None で文書全体が同一キー)。候補を全連結すると判定 LLM 入力が文書まるごとに膨張するため、rationale を逐語で含むチャンクを1つだけ選ぶ。含むものが無ければ先頭候補 (→逐語照合は0になり正しく落ちる)。
再フィルタ用フラグの安全装置: --require-rag-fail (no_match だけ残す) と --require-rag-hit (match だけ残す) は相反するので同時指定は ValueError で早期棄却。また rag_verification 未付与のファイルにこれらを当てると全件 drop するので、1件も rag-verify 済みが無ければ警告して条件を無視、まだら状態なら未付与件数を警告で明示する。
08

RAG 実走検証 — 自己ループの外の信号

rag_verify.py。「生成→判定」の LLM 自己ループから外れた信号を1本入れる段。この QA が素の vector RAG で解けてしまうのかを実際に走らせて確かめ、結果を qa.rag_verification に埋める。

1

検索

質問を Ruri (VLLM_EMBEDDING_MODEL) で埋め込み、チャンク埋め込みとのコサインで top-k を取得。同点時は元順序を保つ安定ソート (量子化で run ごとに結果が揺れるのを防ぐ)。ゼロベクトルは例外に倒す。

2

RAG 回答

上位 k チャンクだけを根拠に、本番想定モデル (--rag-model) が回答。

3

無回答正規化 _is_unable_answer

「回答不能」「不明」「該当なし」「文書からは特定できません」等の言い回しを無回答扱いに揃え、判定 LLM を呼ばない (揺れを match/partial と誤判定させない)。

4

照合

判定 LLM が ground truth と候補回答を照合し match / partial / no_match を返す。想定外 verdict (例 matched) は警告し no_match のまま、生の値を judge_raw に保存。

5

検索命中を2粒度で記録

下記参照。1問ずつ追記書き出しなので、Ctrl-C / API 全断で途中で死んでも処理済み分は残る。

検索命中の2粒度 — 過大評価を避ける

retrieval_hit_doc

根拠と同じ doc_id のチャンクが上位 k に1個でも居れば真。1文書が50チャンクを超える技報では、根拠と無関係な章が入っただけで真になり過大評価。

retrieval_hit_chunk 本命

根拠本文 (rationale.text) を逐語で含むチャンクが上位 k に居れば真。filter と同じ空白正規化。検索健全性を見る本命指標。

旧 retrieval_hit フィールドは doc OR chunk を入れて既存 JSONL と後方互換を保つ。

この結果の使い道: kg_poc では「vector RAG で解けない問い (= KG-RAG が活きる主戦場)」を --require-rag-fail で抜き出せる。general では難易度タグの妥当性チェックに使える。stats の「RAG検証」タブでは 判定LLMが答えあり + 不一致 の QA を「KG候補リスト」として列挙し、目視で当たりを付けられる。
09

プロービング — AXIS-3 を埋める (kg_poc)

probe.py。filter 通過後の QA に、素の LLM が RAG 無しで答えられるか (llm_knowledge = known | unknown) を後付けする。これをやらないと「KG-RAG の主戦場 = unknown」セルに何問あるかが分からない。

STEP 1質問だけを素の LLM に渡す (RAG無し / チャンク非提示)
候補回答を得る。候補が空 or「不明」なら即 unknown (保守的挙動)。
STEP 2判定LLM に「候補回答 vs ground truth」を比較させる
match: known | unknown を取得。判定が壊れたら unknown にフォールバック。
SETqa.llm_knowledge にセット
known を除きたい理由: known (RAG無しでも LLM が答えられる) 問いでは KG の貢献が見えにくい。unknown (RAG必須) こそ KG-RAG で改善余地がある主戦場。probe はこの2値を機械的に振り分ける自動化。
10

根拠検証 — leave-one-out

answer_grounding.py。「rationale[i] を伏せたら answer が決まらなくなるか」を根拠単位ごとに判定 LLM に問う。本丸 (KG-RAG の効きどころ) の必要条件「全 doc が answer に必要」を意味的に確認する。

根拠単位 (evidence unit) = rationale.chunk_id があればチャンク、無ければ doc_id。一文書コーパス (モデル就業規則) では離れたチャンク2つを単位にできる。

各単位についてこの単位の rationale を伏せる → 残りだけで answer の固有値を再現できるか?
判定 LLM が sufficient: true/false を返す。true = その単位は不要 (伏せても answer が決まる)。判定が壊れたら保守的に false (= その doc は必要とみなす)。

全単位が false

= どの単位を伏せても answer が決まらない = 全単位必須。本丸の必要条件を満たす。

1単位でも true

= その単位単独で answer が出る = 片 doc 完結。体裁だけ multi-doc の「監査」行き。

導入の経緯: v3 で判明 — rationale が2 doc 並んでも 17/23 件は片 doc 完結だった。「2 doc rationale」という体裁だけでは本丸判定にならないため、この leave-one-out を後付け判定として導入。永続化フィールドは歴史的名称 per_doc_sufficient を保つが、キーは evidence unit。

LLM ルーティングと堅牢化

llm.py。単一エントリ generate(prompt, model, ...) がモデル名でバックエンドを自動判定する。生成・判定・埋め込みで別モデル/別プロバイダを混在させられる。

バックエンド自動判定 _resolve_backend

model が claude* / anthropic/* → Anthropic
model == AZURE_OPENAI_CHAT_DEPLOYMENT_NAME、または azure/* → Azure OpenAI
それ以外 → vLLM (OpenAI互換)

🔁 再試行 (tenacity)

最大6回、指数バックオフ (min 2s / max 60s)。Azure の流量制限 (429) は枠が60秒で回復するので、待ち上限を60秒まで伸ばして粘る。

🚫 プロキシ無視

httpx.Client(trust_env=False) でシステムプロキシを一切無視。一部環境で POST だけプロキシに握り潰され、GET は通るのに生成だけ落ちる事故を防ぐ。

🧩 JSON 堅牢化

force_json=True で response_format=json_object。パースは ```json フェンス除去 → 最初の均衡 {...} 抽出 の2段で救済。

📐 埋め込み embed

別エンドポイント (VLLM_EMBEDDING_ENDPOINT / Ruri) を叩く。重複検知・多チャンク戦略・RAG検索で共用。L2正規化して使う。

まとめ — このパイプラインが守っている3原則

1

生成と判定を別モデルに分ける

生成 (vLLM Gemma系) の自己満足を、判定 (Azure/Claude) が外から採点する。さらに rag-verify で実走という第3の信号を足す。

2

LLM を通さない決定論チェックを随所に挟む

難易度算出・逐語根拠照合・9段の生成後検査・leave-one-out — LLM が「もっともらしく嘘をつく」経路を正規表現と照合で機械的に塞ぐ。

3

偽の難しさを疑い続ける

「2チャンクだが1文書」「体裁だけ multi-doc」「場所当て」「答えを質問に書いた試験文体」— KG-RAG 評価に値しない不良型を、各段で執拗に検出して落とす。
